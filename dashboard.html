▸ 2.1.1 S3 Bucket Server-Side Encryption FAIL

Why this matters: Without encryption at rest, anyone who gains unauthorized access to the underlying storage can read the raw data directly.

Resources checked:

  • FAIL aws_s3_bucket.insecure_bucket — aws_s3_bucket.insecure_bucket has no server-side encryption configured.

How to fix it: Add an aws_s3_bucket_server_side_encryption_configuration resource for this bucket with sse_algorithm = "AES256".
▸ 2.1.2 S3 Bucket Versioning FAIL

Why this matters: Without versioning, an accidental or malicious overwrite/delete permanently destroys the data — there is no way to recover a prior version.

Resources checked:

  • FAIL aws_s3_bucket.insecure_bucket — aws_s3_bucket.insecure_bucket has no versioning configuration enabled.

How to fix it: Add an aws_s3_bucket_versioning resource for this bucket with status = "Enabled".
▸ 2.1.5.1 S3 Block Public Access FAIL

Why this matters: Disabling this safeguard means the bucket could be made publicly accessible, intentionally or by mistake, exposing its contents to the entire internet.

Resources checked:

  • FAIL aws_s3_bucket_public_access_block.insecure_bucket_access — aws_s3_bucket_public_access_block.insecure_bucket_access has block_public_acls = false. S3 buckets must block public access.

How to fix it: Set block_public_acls, block_public_policy, ignore_public_acls, and restrict_public_buckets to true.
▸ 2.3 RDS Publicly Accessible FAIL

Why this matters: A database reachable directly from the internet is one of the most common real-world breach vectors — attackers actively scan for exposed databases.

Resources checked:

  • FAIL aws_db_instance.insecure_db — aws_db_instance.insecure_db is a publicly accessible RDS instance.

How to fix it: Set publicly_accessible = false on the RDS instance, and access it via a bastion host or VPN instead.
▸ 2.3.3 RDS Storage Encryption FAIL

Why this matters: Unencrypted database storage means raw data is readable if the underlying disk is ever accessed without authorization.

Resources checked:

  • FAIL aws_db_instance.insecure_db — aws_db_instance.insecure_db has unencrypted RDS storage.

How to fix it: Set storage_encrypted = true on the RDS instance.
▸ 5.2 SSH Open to the Internet FAIL

Why this matters: Port 22 open to 0.0.0.0/0 means anyone on the internet can attempt to log into the server — a constant, automated attack target.

Resources checked:

  • FAIL aws_security_group.insecure_sg — aws_security_group.insecure_sg allows SSH (port 22) ingress from 0.0.0.0/0 (entire internet).

How to fix it: Restrict the security group's ingress CIDR block for port 22 to a specific internal range, not 0.0.0.0/0.
▸ 5.3 RDP Open to the Internet FAIL

Why this matters: Same risk as SSH exposure, but for Windows remote desktop access — a very common ransomware entry point in real-world breaches.

Resources checked:

  • FAIL aws_security_group.insecure_sg_rdp — aws_security_group.insecure_sg_rdp allows RDP (port 3389) ingress from 0.0.0.0/0 (entire internet).

How to fix it: Restrict the security group's ingress CIDR block for port 3389 to a specific internal range, not 0.0.0.0/0.
▸ EBS-1 EBS Volume Encryption FAIL

Why this matters: An unencrypted disk volume exposes raw data if the volume is ever improperly detached, snapshotted, or accessed outside its intended instance.

Resources checked:

  • FAIL aws_ebs_volume.insecure_volume — aws_ebs_volume.insecure_volume is an unencrypted EBS volume.

How to fix it: Set encrypted = true on the EBS volume.
▸ IAM-1 IAM Wildcard Policy FAIL

Why this matters: A policy granting Action="*" and Resource="*" gives full administrative control over the entire AWS account to anything using it — a single compromised credential means total account takeover.

Resources checked:

  • FAIL aws_iam_policy.insecure_policy — aws_iam_policy.insecure_policy grants wildcard Action=* and Resource=* (full admin access).

How to fix it: Scope the policy's Action and Resource fields to only the specific permissions needed, instead of "*".
▸ SECRET-1 Hardcoded Credentials FAIL

Why this matters: A password committed directly in source code is visible to anyone with repo access, remains in Git history forever even if later removed, and is a leading cause of real-world credential leaks.

Resources checked:

  • FAIL aws_db_instance.insecure_db — aws_db_instance.insecure_db has a hardcoded plaintext password in source code.

How to fix it: Move the password into a Terraform variable marked sensitive = true, supplied via .tfvars (gitignored) or a secrets manager.
